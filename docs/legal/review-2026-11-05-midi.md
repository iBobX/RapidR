# Legal review, 2026-11-05: MIDI input/output (`RMIDIPort`) on Windows, macOS, Linux and the web

This is the "lawyer agent" review (standing rule since 2026-10-22) for a new component family. It is a careful risk review with sources, **not legal advice** (US/EU practice; Uruguayan law not checked).

- **What is being added:** an `RMIDIPort` component (list devices, open input/output, short messages, SysEx) on Windows, macOS, Linux and the web. Candidate cross-platform layer: the `midir` crate. On the desktop it would reach users' commercial, closed-source programs inside the runner; on the web it would run in the browser through the browser's own MIDI interface.
- **Checked:**
  - the exact dependency tree of `midir` 0.11.1 (the newest release on crates.io, 2026-10-10), resolved in a scratch project at `/Volumes/RapidRBuild/legal-midir/probe` (`cargo metadata`, `cargo tree` for 9 targets: Windows x64 and ARM64 on `msvc` and on `gnullvm`, macOS x64 and ARM64, Linux x64 and ARM64, wasm32; Android and iOS looked at only as a note), then compared with RapidR's `Cargo.lock`;
  - the real files in `~/.cargo/registry/src/` (LICENSE files, `Cargo.toml` feature tables, every source file's header, a text sweep for copyleft and "derived from" statements) for `midir`, `coremidi`, `coremidi-sys`, `alsa`, `alsa-sys`;
  - **real builds:** on this Mac (Apple silicon, macOS 27.2) a release build of a tiny `midir` program, its linked libraries read with `otool -L` and run (it lists ports); in the Ubuntu 24.04 ARM64 VM (already running, I did not start it) a release build, `readelf -d`, `ldd`, `nm -D`; `cargo check` for the four Windows targets, macOS x64 and wasm32;
  - RapidR's own `deny.toml` against the scratch tree: `cargo deny --offline check licenses` ok, `bans` ok, `sources` ok, `advisories` ok (cached advisory database of 2026-10-30; nothing listed for `midir`, `alsa`, `alsa-sys`, `coremidi`, `coremidi-sys`; not refreshed online);
  - RapidR's own code: `crates/rapidr-runtime-core/src/media.rs` and `Cargo.toml` (midir is already used), `crates/rapidr-runtime-web/src/media_web.rs` (Web MIDI is already used), `crates/rapidr-value/src/objects/midiout.rs`, `tools/release/linux.sh`, `crates/rapidr-cli/src/notices.rs`, `docs/licensing.md`, `LICENSES.md`, `LEGAL.md`;
  - on the web: the W3C Web MIDI API specification (sections on permissions, secure context, Permissions Policy, security and privacy), MDN's `requestMIDIAccess`, Chrome's developer blog on the MIDI permission prompt, caniuse; for trademarks: the MIDI Association's pages (SysEx ID policy of 2025-10-15, MIDI 2.0 logo licensing, MMA IP policy, Terms of Use) and a 2018 forum reply of the MMA admin.

- **Not run:** nothing was added to the repository, so `tools/third_party_notices.py`, `rapidr notices <kind>` and `tools/check_notices.py` were not run on the real tree (condition C7). No MIDI hardware was used.

## Verdict: OK WITH CONDITIONS

For the desktop, `midir` is clean: **MIT**, every crate it pulls in is MIT, Apache-2.0 or both (one build-time proc-macro helper also Unicode-3.0), **no file anywhere carries a copyleft header**, RapidR's `cargo deny` passes, and the **dependency delta is zero crates**: every crate `midir` 0.11.1 would pull in is already in `Cargo.lock` by name (RapidR already ships `midir` 0.11.0 for `RMIDI`/QMIDI's MIDI output). The one LGPL piece, `libasound` on Linux, is **dynamically linked from the OS** (verified on a real binary: `NEEDED libasound.so.2`, no ALSA symbol defined inside the program), the allowed exception; macOS CoreMIDI and Windows `winmm.dll` are system libraries that are never shipped.

**One real finding, on the web:** `midir`'s Web MIDI backend **hard-codes `sysex: true`** the first time any port object is created, so every program that only plays notes would still ask the user for the SysEx permission, the strongest MIDI permission, and in the browser's wording at that (condition C2). RapidR already has its own small Web MIDI code that asks without SysEx (`media_web.rs`): the web side of `RMIDIPort` is to extend that, not to use `midir`'s web backend (which also keeps `midir` out of the wasm graph, as it is today).

The other conditions are mechanical or wording: the Linux `libasound2` note for users who package their programs (C4), the "MIDI" name and the SysEx manufacturer-ID rules (C5, C6), what the AI/MCP tools and crash reports may do with port names and SysEx (C8), and the usual notices run (C7).

## 2. File headers and provenance

- **`midir` 0.11.1, every file read for a header or a "derived from" sentence** (24 Rust files, `build.rs`, README, CHANGELOG, `Cargo.toml` and its original): **none of the Rust files has a licence or copyright header at all**; the licence is the crate's `LICENSE` (MIT, "Copyright (c) 2015 Patrick Reisert and the RtMidi contributors") and `Cargo.toml`. A text sweep for GPL/LGPL/MPL/Mozilla/copyright/SPDX/derived/ported/based on/adapted/copied/translated/credit finds only: the README sentence "inspired by RtMidi", the Windows backend's type name `RtMidiInPort` (a name, not a licence), and URLs (MDN). No stray copyleft header (the regalloc2 lesson is not repeated here).
- **RtMidi lineage:** the crate is a Rust re-implementation inspired by RtMidi (Gary P. Scavone, C++), and the LICENSE credits "the RtMidi contributors". RtMidi's own licence (read today from its repository) is the MIT text with one extra paragraph that asks anyone distributing modifications to send them to the original developer, and says in the same sentence that this "is, however, not a binding provision of this license". So even if some logic was ported, the licence on the table is MIT with a non-binding request; nothing to carry beyond the MIT notice that `midir`'s LICENSE already contains. Risk: very low. If a future `midir` replaced its LICENSE with something else, `cargo deny` would show it.
- **`coremidi` 0.9.2, `coremidi-sys` 3.2.1, `alsa` 0.12.1, `alsa-sys` 0.6.1:** same sweep, nothing found (no copyleft, no Apple or LGPL header). `coremidi-sys/src/generated.rs` and `alsa-sys/src/generated.rs` are `rust-bindgen` output (declarations of the system libraries' functions, types and constants); neither crate copies a header file or any implementation.
- **LGPL-2.1 and the `alsa-sys` bindings:** LGPL-2.1 section 5 says code that uses only numerical parameters, data-structure layouts, accessors and small inline functions of a library's header is unrestricted whether or not it is legally derivative. The bindings contain only extern declarations, constants and layouts (no inline function bodies). RapidR's existing position (`docs/licensing.md` §3.3 table, `LICENSES.md` §7) is the same.

The crate contains no C source of ALSA (files: bindings, `build.rs`, `wrapper.h`, licence). It would start to ask for things (LGPL text, an offer of the library's source, allowing relinking) if someone **ships their own copy** of `libasound.so.2` in an AppImage, a Flatpak, a container image or a zip. `LEGAL.md` tells users to list `libssl3` as a dependency on Linux but does not say the same about ALSA (C4).

**Windows (`winmm.dll`; "Windows MIDI").**

## 5. Web MIDI: permissions, consent and privacy

**What the platform does.** The browser's MIDI interface (the W3C "Web MIDI API", a specification of the W3C Audio Working Group) is gated by a user permission named "midi" with a separate, stronger "sysex" level:

- `requestMIDIAccess()` is a secure-context feature (HTTPS, or localhost) and obeys the `midi` Permissions Policy (default: the page itself; an embedded frame needs `allow="midi"`). It "SHOULD prompt the user", especially for SysEx; a denial rejects the promise with `NotAllowedError` (Chrome's post also mentions `SecurityError`). Without the SysEx option, sending SysEx throws and incoming SysEx is silently masked.
- Chrome and Edge: since Chrome 124 the **whole** API (not only SysEx) is behind the prompt (Chrome's developer blog); Opera yes; Firefox from 108 (through its site-permission add-on prompt as Mozilla's announcement described it; I did not try the current Firefox); **Safari and iOS: not supported** (caniuse; a third-party extension exists, which is not WebKit); Chrome for Android from 157 (caniuse).
- The specification itself says why SysEx is separate: SysEx can read or overwrite data stored in a device and, in a theoretical chain of conditions, push firmware; it tells user agents to warn about it and developers to request SysEx only when needed. It also notes that listing devices can help fingerprint a user (name, manufacturer, opaque ID per port).

**The finding about `midir`'s web backend.** `src/backend/webmidi/mod.rs` creates its static state on first use of any `MidiInput`/`MidiOutput`, and that state starts with `request_midi_access(true)`; its own comment says "I've chosen to hardcode sysex=true here". Consequences: (1) a program that only plays notes still asks for the SysEx permission, the most invasive MIDI permission, and in some browsers with the heavier wording; (2) the request happens as a side effect of creating an object (the author cannot decide when); (3) the user who clicks "Block" on a SysEx request has blocked the note-only program too. For a tool whose users ship programs to the public that is the opposite of data minimisation, and the company in the middle is RapidR. **Decision: do not use `midir` on the web.** RapidR already has its own Web MIDI code (`rapidr-runtime-web/src/media_web.rs`): it calls `requestMIDIAccess()` with no options, only when a song is first played, and `midir` is not in the graph of `rapidr-runtime-web` (checked: `cargo tree -p rapidr-runtime-web -i midir` finds no such package). `RMIDIPort` on the web extends that code with inputs, and requests SysEx only if the program asks for it (C2).

**Consent and privacy rules for RapidR's web `RMIDIPort`** (C3):
1. Ask only when the program calls `RMIDIPort` (list or open), never when the page or the runtime loads. Prefer a call that follows a click (so the browser can show the prompt); document that.
2. No SysEx unless the program sets the SysEx property; then a **separate** request; refusing SysEx leaves ordinary messages working.
3. Show a short explanation of RapidR's own **before** the browser's prompt (text below), because the browser's text is the browser's and varies.
4. Handle a refusal as an ordinary, readable error ("MIDI access was not allowed in this browser"), not as a crash; remember nothing about the refusal beyond the browser's own memory.
5. Device names and ids stay inside the page: RapidR's runtime sends them nowhere, logs none, and the web build has no telemetry. (What a **program** does with them, for example posting the list to its server, is its author's data-protection matter: device names can identify a person ("Robert's iPhone") and the set of devices helps fingerprint a browser. `docs/licensing.md` or the Help page says so in one sentence.)
6. Hosting: a RapidR web build is an ordinary page on HTTPS; if someone embeds it in a frame, their page must allow `midi`. The Help page says so.

**Suggested wording** (English; Spanish is the same sense; Portuguese and Chinese through the I18N lane; keep these two sentences, they are the legal content):
- Before the browser's prompt: *"This program wants to use your MIDI devices (keyboards, controllers, synthesizers). Your browser will ask you to allow it. RapidR does not send the list of your devices anywhere. [Continue] [Not now]"* (check the claim again at the time: it is true of RapidR's runtime, not of what a program's own code does).
- Before the SysEx request: *"This program also wants to send and receive "system exclusive" (SysEx) messages. These can change settings stored inside a MIDI device and, on some devices, even replace its firmware. Allow it only for programs you trust. [Continue] [Not now]"*
- Spanish: *"Este programa quiere usar tus dispositivos MIDI (teclados, controladores, sintetizadores). Tu navegador te pedirá permiso. RapidR no envía la lista de tus dispositivos a ningún sitio."* and *"Este programa también quiere enviar y recibir mensajes «exclusivos del sistema» (SysEx). Pueden cambiar ajustes guardados dentro de un dispositivo MIDI y, en algunos, incluso reemplazar su firmware. Permítelo solo para programas en los que confíes."*
- The browser's permission dialog is the legal consent; RapidR's text is information, not a substitute, and must not imply that RapidR itself grants or checks anything.

**Desktop:** Windows and Linux ask for nothing; macOS: the probe ran from a terminal on this Mac and listed ports without error; whether CoreMIDI or the system ever shows a privacy prompt (Bluetooth or Network MIDI devices, App Sandbox) was not checked. Desktop programs are the user's own programs running with the user's rights; SysEx can still alter a device, so the Help page carries the same warning (C6).

## 6. Names, trademarks and the MIDI Association's rules

What was read today and what could not be read (see the header): the MIDI Association's pages say "MIDI is free to use and always will be" and that **no licence is needed to build a MIDI 2.0 product, only to use the MIDI Association's logo** and be listed (MIDI 2.0 logo licensing page; the logo needs a signed agreement, self-certification and membership or a fee). A 2018 reply by the MMA's forum admin says the stylised "MIDI" **logo** is owned by the MMA and "may be used only as defined by MMA", and that a third-party "Web MIDI" logo was **not approved**; it pointed to a trademark-policy page that is a 404 today. The Terms of Use only protect the site's own content. A third-party notice (a vendor's legal page) states that MIDI is a trademark of the MIDI Manufacturers Association registered in many countries and of AMEI in Japan; I could not confirm that against a register.

Reading, conservatively:
1. **"MIDI" as a descriptive word in a component name** (`RMIDIPort`, like the shipped `RMIDI`): it names the standard the component speaks. Same pattern as `RHttp` and `RMySQL`. Low risk. If the owners ever object, the rename is mechanical (the importer/alias machinery exists).
2. **Not allowed, whatever the policy turns out to say:** the MIDI logo or the MIDI 2.0 logo; any claim of certification, licence, approval or membership ("MIDI certified", "MIDI Association approved"); "MIDI" as the name of a **RapidR product** or of a company/project (for example "RapidR MIDI Studio"); "Web MIDI" as a RapidR feature name or logo (it is the name of a W3C specification and of the 2018 logo question; in engineering text and Help it appears only as "the browser's MIDI interface (the Web MIDI API)").
3. **Notice:** add MIDI to the list in `LEGAL.md` "Trademarks" with the usual two lines (named only to say which standard the component speaks; independent of the owners). Suggested wording: "MIDI is a name or mark of its owners (the MIDI Manufacturers Association and, in Japan, AMEI); Web MIDI is the name of a W3C specification." If the policy page becomes readable and asks for other words, use theirs.
4. **Other names:** CoreMIDI (Apple), WinMM and Windows MIDI Services (Microsoft), ALSA, Roland and GS (the existing SysEx example's synthesizer messages), Chrome, Edge, Firefox, Safari: factual identifiers in engineering text and in a support table; `LEGAL.md`'s existing sentence ("other names belong to their owners") plus the usual "named only to say what it works with" covers them. In user-facing Help prefer "the system's MIDI service" and name a browser only in the support table.

**SysEx manufacturer IDs (the MIDI Association's policy of 2025-10-15, read today).** A SysEx message starts with a manufacturer ID, the educational ID `0x7D`, or a Universal ID (`0x7E` non-real-time, `0x7F` real-time). IDs are permanent now (no annual fee); a paid ID costs a one-time $240 (non-voting) or comes with corporate membership from $600 a year, scaled to turnover; `0x7D` is free but "is not to be used on any product released to the public"; `0x7C` is free for public products that make no financial gain and may not be used for custom SysEx data formats. The page does not say whether a library that merely relays bytes a program gives it needs an ID (it is the program's message format that needs one). Reading: `RMIDIPort` is a pipe; sending bytes the program supplies needs no ID from RapidR; but RapidR itself must **not define any SysEx format of its own** (not for the micro:bit/ESP32 plans, not for RAI, not for examples), and its examples use Universal messages (for example the Identity Request `F0 7E 7F 06 01 F7` or "GM System On") or a documented message of a device maker typed in by the user, as `examples/windows/midi_sysex_out.rr` does today. Users who ship a program with their own SysEx format need their own ID (C6 says so in Help).

## 7. Patents and export

- **MIDI 1.0** dates from 1983; the basic messages RapidR handles (note, controller, program, pitch, system real-time, SysEx envelope) are decades old and any patent on them would have expired; nothing here is MIDI 2.0 (UMP, MIDI-CI, Profiles), which is a separate decision. The MMA IP policy (read today) requires members who hold patents necessarily infringed by a compliant implementation of a specification to license them royalty-free on reasonable terms, on reciprocal terms; it names no patent. No third-party patent search was possible. Risk: low.
- `midir`, `coremidi` and `alsa` are MIT / Apache-2.0: Apache-2.0 crates carry its patent grant (`alsa`, `windows`, ...); MIT has none and none is claimed.
- **Export control:** no cryptography in this family; no change to `LEGAL.md` "Export".

## 8. The six traps (CLAUDE.md), for this change

A MIDI port component adds no sign-up, accounts, analytics, email, payments, uploads or children's data. **None of the six applies as a feature.** Notes: (2) third-party assets: no font, script or style is loaded from anywhere; the web code calls the browser's own interface; (3) analytics: none exist and none may be added to MIDI (port names and message bytes in particular stay out of any usage statistics); (1), (4), (5), (6): not applicable. The one data-protection point is that device names can identify a person (section 5, point 5, and C8).

## 9. Product-safety points that are not licence matters

- **SysEx can change what is inside a device** (settings, tables and, on some devices, firmware: the W3C specification's own words). Short messages cannot expose or overwrite stored data. RapidR's Help for `RMIDIPort` carries a warning next to SysEx.
- **AI/MCP:** the plan is that every component is operable by RAI and by MCP. A port list is read-only data; **sending SysEx (and any message to a device) through an AI tool must be an action the user confirms**, like other actions with side effects in the MCP plan, because an agent steered by text in a file or a web page could otherwise write to hardware. The port names returned to an AI tool go to the AI provider the user chose: the tool description says so.
- **Crash reports and logs** (the local, scrubbed crash-report plan): no port names, no ids and no message bytes by default.
