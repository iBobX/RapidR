### SEC-34 — High — `rapidr-webview.html` cross-origin framing → XSS in the program's / Studio's own origin

**Where.** `interpreter/rapidr-webbundle/web/rapidr-webview.html` (the whole
file); shipped unconditionally by `interpreter/rapidr-webbundle/src/lib.rs:161`
(`page_files`) and `:329` (`native_site_files`), and copied into the Studio web
build at `runtime/rapidr-webview.html` (`tools/build_studio_web.sh:52`). The
framing control (`frame-ancestors`) is emitted for `index.html` only:
`interpreter/rapidr-webbundle/src/lib.rs:362-363` (`_headers`, paths `/` and
`/index.html`) and `:377` (`.htaccess`, `<Files "index.html">`); the same for
Studio's `ide/web/_headers:13-16` and `ide/web/.htaccess:17-19`.

**The gadget.** `rapidr-webview.html`'s entire body is:

```html
<script>
addEventListener("message", function (e) {
  if (e.source !== parent || !e.data || typeof e.data.__rapidr_webview_html !== "string") return;
  document.open();
  document.write(e.data.__rapidr_webview_html);
  document.close();
});
</script>
```

It `document.write`s whatever string its **parent** posts, with **no origin
check** and **no CSP of its own**. In the intended flow the parent is the
program's own (same-origin) page, so the HTML is the author's — that is the
whole SEC-15 design (run the RWEBVIEW's `Html` here so it does *not* inherit
the program page's strict CSP). The file carries this trust-your-parent
assumption, and the only thing meant to keep a hostile parent out is
`frame-ancestors`.

**The gap.** `frame-ancestors 'self'` is set on `index.html` only — the code
comment even says `rapidr-webview.html` "must not get it", conflating "don't
give this file index.html's content-restricting CSP (which would stop the
RWEBVIEW HTML's own scripts)" with "don't restrict who may frame it". A `<meta>`
CSP cannot express `frame-ancestors` at all, so on a plain static host (GitHub
Pages, S3, `python3 -m http.server`) nothing restricts framing of any file. On
a host that honours `_headers`/`.htaccess`, everything except `index.html` —
`rapidr-webview.html` among them — is framable by any origin. (`Cross-Origin-Resource-Policy:
same-origin`, set on `/*`, does **not** block document framing; confirmed in
the PoC below, where CORP is present and framing still succeeds.)

**The attack.**
1. The attacker page `evil.example` embeds `<iframe src="https://victim-app/rapidr-webview.html">`.
2. Inside that iframe, `window.parent` is `evil.example`.
3. `evil.example` does `iframe.contentWindow.postMessage({ __rapidr_webview_html: "<img src=x onerror=…>" }, "*")`.
4. The guard `e.source !== parent` passes (the sender *is* the parent), and
   `document.write` runs the attacker's markup **in the victim app's origin**.
5. That markup now runs as the victim origin: it reads and writes the victim's
   `localStorage` (a program's `RWEBSTORAGE`, QREGISTRY's `rapidr.registry`;
   **for Studio-web, `dev.rapidr.keys.<provider>` — the developer's AI API
   keys** — and `dev.rapidr.ai.audit`), its cookies, and makes same-origin
   fetches as the user.

The popup vector (`window.open` of the file) is **not** exploitable: a
top-level window has `parent === self`, so the opener's message has
`e.source !== parent` and is ignored. Only **framing** works, because there
the parent is the attacker. This is why `frame-ancestors`/an origin check is
the exact missing control.

**Worst case.** Studio-web. `https://<studio-host>/runtime/rapidr-webview.html`
is framable; a script run in the Studio origin reads the AI keys straight out
of `localStorage` (`rapidr-ai/src/keys.rs:655-668`, item `dev.rapidr.keys.<name>`)
and exfiltrates them. Every deployed web program is also affected: the file
ships in **every** bundle, even programs that never use RWEBVIEW.

**PoC (reproduced locally, headless Chromium).**
`tests/security/open/webview_frame_xss.mjs` serves the **real shipped
`rapidr-webview.html`** on one loopback origin (the "victim app", with the
bundle's own `_headers` set, CORP included) and an attacker page on a second
loopback origin (a different port = a different origin). The attacker frames
the victim's `rapidr-webview.html` and posts an `<img onerror>` payload that
beacons the victim origin. Result:

```
victim origin:   http://127.0.0.1:58001
attacker origin: http://127.0.0.1:58002
beacons to the victim origin: ["/XSS_PROOF?origin=http%3A%2F%2F127.0.0.1%3A58001"]
VULNERABLE: attacker markup executed in the victim app's own origin via
rapidr-webview.html (cross-origin framing + parent postMessage).
```

The beacon carries the **victim's** `location.origin`, proving the code ran as
the victim, across the origin boundary. The PoC is in `tests/security/open/`
(not `tests/security/*.mjs`), so `tools/regress.sh security` does not run it
and the build stays green; run it by hand with
`node tests/security/open/webview_frame_xss.mjs` (needs the repo's
`tests/node_modules`: Playwright + chromium; loopback only).

**Recommended fix (two layers; the file-level one is the robust one).**
1. **In `rapidr-webview.html`, also require the HTML to come from a same-origin
   parent:** add `e.origin === location.origin` to the guard. For a deployed
   program the legitimate parent (the program's page) is same-origin, so this
   passes; `evil.example` has a different origin and is blocked. For the Studio
   run-frame case both the frame and its parent are *opaque* (origin `"null"`),
   so the legitimate case still passes, and a third-party framer of
   `runtime/rapidr-webview.html` sees the real Studio origin on one side and
   its own on the other, so it is blocked. This works on every host, including
   the static ones a `<meta>` CSP can't protect.
2. **Emit a framing control for the file too:** give `rapidr-webview.html`
   (and, defensively, every non-`index.html` HTML file) `frame-ancestors 'self'`
   in `_headers`/`.htaccess` (and the Studio build's), as defence-in-depth for
   hosts that honour headers. Do **not** give it `index.html`'s full policy
   (that part of the original reasoning stands — it would break the RWEBVIEW
   HTML's own scripts); `frame-ancestors` alone does not.

**Regression to add with the fix:** promote `tests/security/open/webview_frame_xss.mjs`
to a run-by-default check (it is already dependency-light apart from
Playwright; pair it with a source-pin like `web_shipping.mjs` that asserts the
`e.origin` guard is present and that `host_config_files` covers the frame file),
so a future edit can't drop the guard again.

### SEC-35 — Medium — A link can drive RapidR Studio on the web (`?do=` / `?open=`)

**Where.** `ide/web/studio.js:22-23`: the page passes the URL's `?do=` through
verbatim as `--do`, and `?open=` as the start file, with no gate. `ide/shell.inc`
`StartStudio` reads `--do` into `DoList` and sets `Macro.Enabled = 1`;
`MacroTick` then runs each step: `EditorStep` (`ide/editor.inc:270` —
`type:<keys>` sends keystrokes via `Application.SendKeys`, `key:<chord>` sends
a chord, `focus:<pane>`), `PanelStep` (`ide/panels.inc:1155` — `tool:`, `prop:`,
`code:<old>=><new>` which edits the active document, …), `DebugStep`,
`SafetyStep`, else `RunCommand <id>` (any command id).

**Reasoning.** On the desktop `--do` is a CLI flag (the person starting
`rapidr ide` is trusted; it is how the test harness drives Studio). On the web
it is **reachable by any link**: `https://<studio-host>/?do=…` opens Studio and
runs the steps, with no same-site check, no confirmation, and no `window.RAPIDR_STUDIO_TEST`
gate (unlike the other test hooks, SEC-24). The index.html comment lists `?do=`
as a documented parameter, so it is an intended capability — but it grants a
third-party link broad authority over the user's Studio and open project:
inject keystrokes (`type:`/`key:`), edit the active document (`code:`), and run
arbitrary command ids. A crafted link could, unattended, type a program that
reads the project's own files and uses `RHTTP` to send them out, then run it;
or change settings through commands. The run itself is contained to the opaque
frame (it cannot read Studio's keys — that is the SEC-34 boundary, intact
here), so this is a drive/CSRF/keystroke-injection surface, not a direct key
read; hence Medium, and noisy (steps print to the Output pane, one per tick).

**Not separately PoC'd:** a Studio-web build (`tools/build_studio_web.sh`,
which needs `target/web`) is required to exercise it; the path is precise and
read end to end (studio.js → shell.inc `StartStudio`/`MacroTick` →
`EditorStep`/`RunCommand`).

**Recommended fix.** On the web, do not honour `?do=` from the URL unless the
test gate is set (`window.RAPIDR_STUDIO_TEST`, as the GUI test hooks already
require), **or** restrict URL-borne `?do=` to an allowlist of safe, read-only
navigations (e.g. `manual:`, opening an example) and refuse `type:`/`key:`/`code:`/
`RunCommand` from a navigation the user did not initiate in Studio. Treat
`?open=` the same as any file-open (it opens, not runs — lower risk — but it
should still only reach the page store / examples, which it does today).

### SEC-36 — Low — A program's frame can pin itself over Studio's main window (`held`)

**Where.** `ide/web/run.html:362-365` sends `{ __rapidr_windows: { held: true } }`
on `pointerdown` and `{ held: false }` on `pointerup`/`cancel`;
`ide/web/studio.js:299` and `:313-317` (`clipToWindows`) set the program
frame's `clip-path` to `none` whenever `run.held` is true, so the whole frame
(viewport-sized, `pointer-events: auto`) receives input.

**Reasoning.** `held` is entirely frame-controlled. A hostile program can send
`held: true` and never send `false`, so its frame stays un-clipped —
covering all of Studio's main-window area and taking every pointer event
there; if the user clicks, focus moves to the frame and keystrokes follow. The
frame is `z-index: 10` (over Studio's main window) but under Studio's dialogs
and menus (`11+`), and `followPopups` drops it to `z-index: 9` while a Studio
pop-up is open, so it cannot cover Studio's own prompts/menus (good — the
clickjacking of Studio *dialogs* is already handled). What remains is that the
program can present a full-surface fake (e.g. a spoof "enter your API key"
panel that looks like Studio's) over the editing area and capture what the user
types into it. A program's windows covering the IDE is by design (as on the
desktop), and the frame is opaque-origin so it still cannot *read* Studio; the
new element is the persistent, chrome-less, full-region interception. Low:
needs the user to run a hostile program (attacker #1), the data boundary holds,
and pixel spoofing is partly accepted by design.

**Recommended fix.** Treat `held` as a hint tied to a real pointer the host can
see: only honour `held: true` while Studio itself observes a pointer button
down (or for a short, bounded window after one), and otherwise keep the
window-rectangle clipping. Optionally cap how long `held` may stay set without
a corresponding `pointerup`.

### SEC-37 — Info — `$INCLUDE "../x"` lacks the explicit `../` guard the data-file path has

**Where.** `crates/rapidr-project/src/implicit.rs`: `add_named_files` (`:189`)
rejects a data file whose resolved path `starts_with("../")`; `add_includes`
(`:214`) has no equal check. `normalize_path` (`crates/rapidr-project/src/project.rs:665`)
keeps a leading `..`.

**Reasoning.** On the web — this area — it is harmless: includes resolve
through the page's file store (`object_web::web_read_file` → `saved_name` /
`asset_bytes`, keyed by `file_key`, which keeps `../`), and the store never
holds a `../` key (keys come from project paths and from directory-picker
entries, which never contain `..`), so a `../` include matches nothing. It is
noted because `program_files` (which feeds the sandboxed frame) and the
desktop/MCP analysis share this resolver; on the desktop, includes follow
RapidQ's rules (any path the program names) by design for the project's owner,
and Studio's own analysis is intentionally unconfined (SEC-18 fix). If an MCP
or other *remote*-driven context ever runs `implicit_from_resolver` over an
untrusted project, give `add_includes` the same `../`/confinement check
`add_named_files` has.

## 2. Checked and found sound (so the next audit need not redo these)

**The program ⇄ Studio boundary (the primary web boundary).** `ide/web/run.html`
runs the program in an iframe created with `sandbox="allow-scripts allow-modals
allow-downloads"` — **no `allow-same-origin`** (`ide/web/studio.js:351`), so the
program is at an opaque origin and cannot reach Studio's DOM, `localStorage`
(keys/chats) or OPFS. The boot handshake holds: `run.html` posts `__rapidr_hello`
to `parent` only; `studio.js`'s `hello` accepts it only when
`e.source === frame.contentWindow`, then hands a private `MessageChannel`;
`run.html`'s boot accepts `__rapidr_boot` only when `e.source === parent` and
once (`booted`), and everything afterwards flows over the private port, window
messages ignored. The SEC-14 font bridge guard is in place
(`studio.js:265`, `/^[\w.-]+$/` + no `..`), pinned by
`tests/security/web_font_bridge_traversal.mjs`.

**The web-only components (`overlay_web.rs`).** RWEBVIEW's default sandbox is
`WEBVIEW_SANDBOX` = `allow-scripts allow-forms allow-popups allow-modals
allow-downloads` — no `allow-same-origin` (SEC-12); its `Html` with scripts
runs in `rapidr-webview.html` (never an `srcdoc` that would inherit the page
policy), the frame is given its HTML only while it still shows the frame file
(`show_html`, the `frame.src() != webview_frame_url()` check), and
`win.post_message(&msg, "*")` is sound because an opaque frame can't name its
target origin and the frame file is the one listening. RDOM's `InnerHTML` /
`SetAttribute` are author-controlled markup by design and bounded at the
deployed layer by the per-bundle CSP (see below). (The separate weakness is
the *standalone* `rapidr-webview.html` file being third-party-framable —
SEC-34 — not the in-page RWEBVIEW wiring, which is correct.)

**Per-bundle CSP (`csp.rs`).** `WebNeeds::scan` opens only what the program
uses; a plain program gets `script-src 'self' 'wasm-unsafe-eval'`, `object-src
'none'`, `base-uri 'none'`, `frame-src 'none'`, and `connect-src 'self' data:
blob:`. `'unsafe-eval'` only for RJAVASCRIPT; `frame-src`/`https:` only for
RWEBVIEW; `connect-src https: wss:` only for network components. `add_extra`
(`--csp`) validates directive names against `DIRECTIVES` and rejects a source
containing `; , ' " < > \` (`valid_source`), so an author addition can't break
out of the policy or inject another directive. Verified by the crate's tests
and `tests/web_bundle_csp.mjs` (real browser).

**Name escaping into generated pages (`escape.rs`).** `html` escapes `& < > "
'` and control chars; `js_string` additionally `\u`-escapes `< > & '` and the
line separators so no project/asset name can close a `<script>` or change it;
`url_component` percent-encodes everything but the unreserved set; `file_name`
strips path separators and leading dots (no `..`, no hidden file). The title is
HTML text, the program name an attribute, asset names only string literals in
`rapidr-assets.js`; no name is written into a script. Pinned by
`tests/security/web_bundle_injection.rs`.

**The on-page console (`bundle_console.js`, `ansi_screen.js`).** Printed text
only ever becomes text nodes; coloured runs set `style.color`/`backgroundColor`
from a fixed 16-entry palette by numeric index; CSI parsing is bounded. No
`innerHTML`, no attribute from program data.

**The accessibility mirror (DOM injection? — `mirror.rs`, `aria.rs`).** Tags
are a fixed set (`div`/`input`/`textarea`/…, `aria::tag`); attributes are
`role` and `aria-*` with fixed names and values derived from the kernel's
accessibility tree; node text is written with `set_text_content` (never
`inner_html`); `name`/`autocomplete` come from the component's AutoComplete.
No program string reaches `innerHTML` or an attribute *name*. Sound.

**File import/export in the browser (`file_picker_web.rs`, `object_web.rs`).**
Pickers open only within a user gesture (`gesture_active`); `showOpenFilePicker`/
`showSaveFilePicker` are shown directly only when the page is top-level and not
opaque (`direct` checks `w.origin() != "null"` and top == self), else through
the IDE's `RAPIDR_FILE_HOST`, else `<input type=file>` — in every case the user
picks the file. Writes go only to a handle the user's pick produced (or a
download). Downloads use a Blob + object URL with the content and file name
passed as data (`trigger_download`, `web_print`), never spliced into script. A
web program reads only files the user picked this session, the project's own
assets, or files shipped beside the page — `web_read_file`'s XHR fetches
relative page URLs, never an arbitrary origin.

**Web storage / keys (`storage_web.rs`, `keys.rs` wasm store, `studio.js`
app-storage).** A program's `RWEBSTORAGE` in Studio is kept per program under
`rapidr-app-storage:<program>` and capped at 1 MB (`applyAppStorageOp`), never
touching Studio's own keys. Studio's keys on the web live in `localStorage` as
`dev.rapidr.keys.<name>`; the strict `index.html` CSP is their only guard — so
SEC-34 (which runs script in that origin) is exactly what defeats it, and is
why SEC-34 is High.

**`rapidr serve` (Run in Browser).** Binds `127.0.0.1` only; a request whose
`Host` isn't `127.0.0.1:<port>`/`localhost:<port>` → 421 (DNS rebinding); only
GET/HEAD (else 405); everything outside the random 128-bit `/<token>/` path →
404; `index.html` carries the bundle CSP; every reply `nosniff` + `no-store` +
`Referrer-Policy: no-referrer`; ends when stdin closes. The browser is opened
with the URL as a single argument (no shell). Sound. (Its token guards the
*address*, not authentication — stated in the file; acceptable for a local,
short-lived, loopback dev server.)

**The web debugger / session protocol (`channel.rs`, `session.rs`).** The
untrusted frame sends protocol Events (`Event::from_json`; a non-event is kept
as opaque Text); Studio turns them into `onoutput`/`onstopped`/`oncontinue`/
`onexit`/`onformshown`/`onapp`/reply events handled by `studio.rrbc`
(debug.inc), which display values in canvas-drawn panes — no file write, no
code execution, no DOM injection is triggered by a frame event. Set-value /
evaluate run the user's typed expression by design and only while paused
(SEC-29, fixed). The frame's `__rapidr_windows` rectangles are clamped to the
viewport, finite, and capped at 256 (`studio.js:302-309`). Sound apart from the
`held` hint (SEC-36).

**Supply chain / what the Studio build ships (`build_studio_web.sh`,
`web_shipping.mjs`).** The build copies fixed files (runtime, the RWEBVIEW
frame, icons, lang catalogs, and `examples` from git's own file list); no CORS,
`frame-ancestors 'self'` on `index.html`. (The frame-ancestors gap on
`runtime/rapidr-webview.html` is SEC-34.)

## 4. Fixed (SEC-FIX-WEB, 2026-11-05)

Each fix has a regression test that failed before it and passes after.

- **SEC-34 — fixed.** Fixed in deb3c91b.
  - `rapidr-webview.html` takes the Html only from its parent, and only when
    `e.origin === location.origin` (the program's own page) **or** both this
    frame and its parent are opaque (`self.origin === "null"` and
    `e.origin === "null"`: Studio's program frame). The audit's note that
    Studio's case passes `e.origin === location.origin` doesn't hold in a
    browser: measured in Chromium, inside a sandboxed frame `location.origin`
    is the address's origin (Studio's), while the opaque `run.html` sends
    with `e.origin === "null"`. The literal check alone would have broken
    every RWEBVIEW `Html` in Studio; the opaque-pair rule keeps it, and is
    safe because what runs then is at an opaque origin with no storage. A
    page with no origin of its own (a `data:` frame) framing the file
    unsandboxed is refused by the same rule.
  - Its own policy, from the headers only: a `<meta>` policy in the file
    would stay in force after `document.write` and bind the RWEBVIEW's own
    Html (measured), so the file has none.
    - Bundles (`host_config_files`, both `_headers` and `.htaccess`, also for
      `rapidr build --web`'s site): `/rapidr-webview.html` gets
      `frame-ancestors 'self'` (`WEBVIEW_FRAME_POLICY`), never the page's
      content policy.
    - Studio (`ide/web/_headers`, `.htaccess`): `frame-ancestors 'self'`
      can't be used for `runtime/rapidr-webview.html` — its real ancestor
      `run.html` is opaque and Chromium matches no opaque ancestor to
      `'self'` (measured: Studio's RWEBVIEW stopped loading). It gets
      `sandbox allow-scripts allow-forms allow-popups allow-modals
      allow-downloads` instead: opaque whoever frames it, so nothing in it
      reaches Studio's storage (the AI keys).
    - `rapidr serve` (Run in Browser): `index.html` now gets the header
      policy with `frame-ancestors`; the frame file gets its own policy.
      Before, it got the page's content policy, which also blocked its
      inline script: an RWEBVIEW's `Html` with scripts showed nothing there.
    - `tools/build_studio_web.sh` refuses to build when the copied
      `_headers`/`.htaccess` lack the frames' rules.
  - The same class, found while fixing: `ide/web/run.html` took its boot
    message (with the runtime it imports) from any parent and had no
    `frame-ancestors`. It now boots only when `e.origin === location.origin`
    (Studio's page), and Studio's headers give it `frame-ancestors 'self'`.
